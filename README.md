🧠 Design Philosophy
（本フレームワークにおける設計思想）

本リポジトリは、非同期タスク間通信を扱う際に発生しがちな 複雑性・責務の曖昧化・運用負荷 を抑制することを目的として設計されています。
ここで示す設計方針は、あくまで私自身の経験と思想に基づく 一つの実装例 であり、特定の用途や環境に対して「唯一の正解」を示すものではありません。

以下は、本フレームワークを構築する際に重視した主要な考え方です。

1. 責務境界の明確化
非同期タスク間通信では、
「どのタスクがどの状態を変更できるか」が曖昧になると、
デバッグ困難な不具合や予期しない副作用が発生しやすくなります。

そのため本フレームワークでは、

タスク A → B の依頼と
B → A の返答

を明確に分離し、
発火主体（誰が誰にメッセージを送れるか）を厳密に制御 しています。

返答は callback 登録方式を採用し、
タスク内部の状態変更は 必ずそのタスク自身が行う という原則を維持しています。
（callbackについてはまだ未実装）

2. API の増殖を抑えるためのプロトコル統一
機能追加のたびに API が増えると、
結合テストの組み合わせが指数関数的に増加し、
運用コストが急激に上昇します。

そのため API は以下の 3 種類に統一しています。

init
message
shutdown

機能単位ではなく プロトコル単位で統一する ことで、
API の肥大化とテスト負荷の増加を抑制しています。

3. イベント駆動の自由度を制御する
イベント駆動は柔軟ですが、
無制限に許容すると「任意タスクが任意タスクを揺らす」構造になり、
システムの保守性が著しく低下します。

本フレームワークでは、

発火主体の制限
callback の所有権管理
タスク内部への責務閉じ込め

を徹底し、
自由度よりも構造の安定性を優先 しています。

4. 複雑性の“先回り抑制”
非同期処理では、以下のような問題が後から顕在化しがちです。

queue の無限蓄積
cancellation の整合性崩壊
shutdown race
intent の肥大化
ABI 境界の破壊
message handler の巨大化

これらを「発生してから対処する」のではなく、
設計段階で構造的に発生しにくい形にする ことを重視しています。

5. 人間が運用できる構造であること
農業データの取り扱い経験から、
「人間が扱える構造であること」は非常に重要だと考えています。

そのため、

過度なネストを避ける
データ構造を単純化する
CSV や手作業での修正を想定する
差分更新を追いやすくする

といった 現場運用を前提にした設計 を採用しています。

6. ABI 境界を意識したレイヤ分離
本フレームワークは、

UI：C#
アプリ層：C#
API：C（ABI）
ENGINE：C++
という構成を前提にしています。

ABI 境界を明確にすることで、

言語間の責務分離
メモリ管理の明確化
将来的な差し替え容易性

を確保しています。

 Notes
（注意事項）
本フレームワークは 特定用途に最適化された実装例 であり、すべての環境・要件に適合することを保証するものではありません。
設計思想はあくまで私個人の経験に基づくものであり、他のアーキテクチャやフレームワークを否定する意図はありません。
実運用環境では、要件・性能・チーム構成に応じて適切にカスタマイズすることを推奨します。

Summary
（まとめ）

本リポジトリは、
非同期タスク間通信における複雑性を抑制し、責務を明確化するための一つのアプローチ を示すものです。

「正解」ではなく「参考例」。
しかし、非同期設計で悩む人にとって、
何らかのヒントや指針になれば幸いです。
